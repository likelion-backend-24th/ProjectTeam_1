## 🔍 원인 분석

- 패키지 구조를 미리 잡아두면서 ReplyCommentController.java를
껍데기 상태(import 3줄만 있고 실제 메서드는 없음)로 dev에 먼저 커밋해둠
- 같은 파일 경로에 대해, 내 브랜치는 등록/조회/수정/삭제 로직이
전부 구현된 완성본을 갖고 있었음
- 두 브랜치가 같은 파일을 서로 다른 내용으로 갖고 있는 상태(both modified)에서
git pull(내부적으로 merge)을 실행하니, Git이 어느 쪽 코드를 남겨야 할지
자동으로 판단하지 못해 충돌 발생

---

## 🛠 해결 방법

1. git pull origin dev → 자동 병합 실패, git status로 충돌 파일(both modified) 확인
2. cat으로 파일을 열어 <<<<<<< HEAD / ======= / >>>>>>> 마커 확인
- HEAD 쪽: 내가 작성한 완성 코드
- 마커 아래쪽(커밋 해시 표시): dev의 빈 껍데기 코드
1.  VS Code로 파일을 직접 열어, 마커 3줄과 dev 쪽의 불필요한 코드를 삭제.
완성된 내 코드만 남김
2. git add . → git commit -m "fix: merge conflict 해결" → git push
3. PR 페이지에서 충돌 경고가 사라진 것 확인

---

## 🧠 배운점

- both modified라는 표시가 같은 파일을 양쪽 브랜치가 각각 수정했다는 뜻, 이 경우에 git이 자동으로 합칠 수 없어서 사람이 직접 골라줘야 한다는 걸 경험
- 충돌 마커의 구조를 처음 봤는데 이해하고 나니 지우면 된다는걸 경험
- 앞으로 새 기능 브랜치를 생성 할 때 담당 파일이 dev에 이미 플레이스홀더로 존재하는지 확인하는 습관을 들이고 또 발생하더라도 지우면 될 것 같다
