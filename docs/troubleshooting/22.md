## 📌 문제 발생

1.빌링키(카드)를 등록한 적 없는 사용자가 회원 탈퇴를 시도하면 500 Internal Server Error 발생

2.프론트에는 "서버 내부 오류가 발생했습니다"라는 일반 에러만 노출되어 원인 파악이 어려웠음

---

## 🔍 원인 분석

1. 1차진단
   BillingKeyService.revokeMyBillingKey()가 활성 빌링키가 없으면 CustomException(BILLING_KEY_NOT_FOUND)을 던지는데, 이걸 호출부에서 못 잡아서 그대로 500이 되는 거라 판단.

AuthService.withdraw()에 try-catch를 추가해서 BILLING_KEY_NOT_FOUND만 무시하고 넘어가도록 수정 → 배포했는데도 여전히 500 재현. 2. 2차진단 (서버 로그 확인 후)

실제 예외는org.springframework.transaction.UnexpectedRollbackException: Transaction silently rolled back because it has been marked as rollback-only.

AuthService.withdraw()와BillingKeyService.revokeMyBillingKey() 둘 다 @Transactional이 걸려있고, 기본 전파 방식(REQUIRED)이라 같은 물리적 트랜잭션을 공유.

revokeMyBillingKey() 내부에서 CustomException이 발생하면, Spring이 그 시점에 트랜잭션 전체를 rollback-only로 표시해버림.
이후 withdraw()의 try-catch가 예외를 잡아서 정상 흐름인 것처럼 나머지 로직(리프레시토큰 삭제, 상태 변경)을 계속 진행시켜도, 메서드 종료 시 커밋을 시도하는 순간 Spring이 "이 트랜잭션은 이미 rollback-only로 찍혀있다"며 커밋을 거부하고 UnexpectedRollbackException을 던짐.

예외를 던지고 밖에서 잡아서 무시하는 방식은, 같은 트랜잭션에 참여하는 메서드 사이에서는 통하지 않는다 — 트랜잭션 오염은 예외를 캐치하는 것과 별개로 이미 발생해버린 상태

---

## 🛠 해결 방법

- 예외를 던지고 잡는 대신, BillingKeyService에 hasActiveBillingKey(userId) 메서드를 추가해 활성 빌링키 존재 여부를 예외 없이 먼저 확인
- AuthService.withdraw()에서는 빌링키가 있을 때만 revokeMyBillingKey()를 호출하도록 변경 → 애초에 예외 발생 자체를 차단

---

## 🧠 배운점

- 같은 트랜잭션(같은 전파 범위) 안에서 발생한 예외는, 상위에서 catch해서 무시해도 트랜잭션 자체는 이미 rollback-only로 마킹된 상태라 되돌릴 수 없음
- 정상 흐름에서 발생 가능한 예외를 흐름 제어용으로 쓰려면, @Transactional(propagation = REQUIRES_NEW)로 독립 트랜잭션을 주거나, 애초에 예외가 발생하지 않도록 사전 조회로 분기하는 게 안전
