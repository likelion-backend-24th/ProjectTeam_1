# 사례 2 - 인증 모듈 중복 구현으로 인한 아키텍처 충돌

기술 스택: Git, JAVA
생성일: 2026년 8월 7일 오전 11:28
참고인: 김종범, 승욱 곽, songsihun, gh, KimDasom
Multi-select: 해결

## 📌 문제 발생

1. 문제 유형 (핵심 태그) 정의

- Git 협업 / 브랜치 관리
- 아키텍쳐 충돌 ( 동일 기능 중복 구현) - 팀원 부재(개인사정)로 인한 상황
- 인증/인가 (Security, JWT)
1. 어떤 기능에서 문제가 발생했는가?
- dev 브랜치 최신화 고자어에서 SecurityConfig, JwtAuthenticationFilter, CustomUserDetails 등 인증 관련 파일 3~4개에서 병합 충돌 방생
- 코드라인 충돌이 아닌 같은 역할(JWT 토큰 생성/검증, 인증필터)을 두사람이 각자 독립적으로 구현하면서 모든 구조 자체가 완전히 다른 두개의 인증 시스템 발견

---

## 🔍 원인 분석

1. 소통 부재로 인한 병렬 구현이 진행
2. 파일별 상세 비교
- CustomUserDetails
    - dev 버전 : userId, email, roleType을 각각 개별 필드로 저장
    - A팀원 브랜치가 merge하려던 버전: User 엔티티를 통째로 필드로 보유
    - 데이터 접근 방식 자체가 다름 (getUserId() vs getUser.().getId()
    
- SecurityConfig / JWT 관련 클래스
    - A팀원 : JwtTokenizer + JwtAuthenticationFilter (파라미터 2개: jwtTokenizer, customUserDetailsService)
    - E팀원 : JwtProvider + JwtAuthenticationFilter(파라미터 1개: jwtProvider)
    
    → 이름만 다른게 아니라 생성자 시그니처 자체가 달라 완전히 별개의 클래스. 파일 부분적으로 합치는 방식으로는 해결 불가능하고 한쪽을 통째로 선택해야 하는 상황
    
- 패키지 구조 차이
    - A팀원 : global.filter , global.exception 으로 역할별 분리
    - E팀원 : JwtProvider, JwtAuthenticationFilter, CustomAuthenticationEntryPoint, CustomAccesDeniedHandler를 global.security 패키지 하나에 통합
    
- 기능차이
    - E팀원 :  CustomAccessDenieHandler 존재 (401=미로그인, 403=권한부족을 구분 처리)
    - E팀원 : .requestMatchers("/api/admin/**").hasRole("ADMIN") 같은 관리자 전용 경로 권한 분기 존재
    - A팀원 : CORS 설정(corsConfigurationSource), formLogin/httpBasic 명시적 disable 존재 (D팀원 쪽엔 CORS 설정 자체가 없어 프론트 연동 시 문제 발생 가능)
- UserRepository, CustomUserDetailsService는 상대적으로 단순 병합 가능한 수준으로 확인

## 🛠 해결 방법

- CustomUserDetails
    - 8월 6일 김갑석 강사님과의 피드백으로 getUserId() 접근방식으로 변경
    - ※ 추가 논의 : 유저 상태(Stagtes) 추가
        - 추가 이유:  해당 값이 없을 경우 이용을 할 수 없는 회원이 토큰을 무단으로 사용하여 이용할 수 있는 위험도가 있어 방지를 위함
        - 적용 코드
        
        ```
        publicCustomUserDetails(User user) {
        		...
            this.status= user.getStatus();
        }
        ```
        
    
- SecurityConfig / JWT 관련 클래스
    - 피드백을 받아서 고쳤던 E팀원의 클래스로 선택 후 원래 담당이던 A팀원이 수정
    - 수정과정에서 서로의 코드에 부족한 부분 추가(CORS, CustomAuthenticationEntryPoint)
    
- 패키지 구조 차이
    - A팀원 쪽: 역할별로 패키지를 분리 - 필터는 global.filter예외/인증 실패 처리 관련 클래스(CustomAuthenticationEntryPoint 등)는 global.exception에 위치
    - D팀원 쪽: 인증/보안 관련 클래스(JwtProvider, JwtAuthenticationFilter, CustomAuthenticationEntryPoint, CustomAccessDeniedHandler)를 global.security 패키지 하나로 통합
    - 결정: D팀원의 global.security 통합 구조를 기준으로 패키지 구조 통일
    
- 기능 차이
    - 두 브랜치에 각각만 있던 기능을 모두 살려 하나로 병합하기로 결정
    - E팀원 쪽 기능 채택: CustomAccessDeniedHandler(401/403 구분 처리),/api/admin/** 경로 ADMIN 권한 분기
    - A팀원 쪽 기능 채택: CORS 설정(corsConfigurationSource),formLogin/httpBasic 명시적 disable
    - 두 기능 모두 실제 서비스 동작에 필요한 요소로 판단되어 양쪽 다 누락 없이 최종 SecurityConfig에 반영

## 🧠 배운점

- 인증처럼 프로젝트 전반에 영향을 주는 공통 모듈은, 시작 전에 담당자를 명확히 지정하고 진행 상황을 자주 공유하지 않으면 이런 식으로 같은 기능이 중복 구현될 수 있다는 것을 실제로 경험함
- 병합 충돌에는 두 종류가 있다는 걸 체감
    - 같은 파일을 살짝 다르게 고친 경우 → 코드만 보고 판단해서 해결 가능
    - 아예 다른 설계로 같은 기능을 각자 구현한 경우 → 혼자 판단하지 말고 반드시 팀 논의
- 각 버전의 장단점을 정리해두면, 팀이 "어느 쪽이 낫다"를 감이 아니라 근거를 갖고 판단할 수 있어 결정이 빨라짐 (예: CORS 설정 유무, 403 처리 유무는 실제 서비스 동작에 직결되는 명확한 판단 기준이 됨)
